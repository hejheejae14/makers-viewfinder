# 1-1. 인덱스 생성 및 동기화

팀별 등록 디자인 파일의 모든 페이지와 `[PD] 문서 모음`의 허용 페이지를 읽어 통합 검색 인덱스를 만드는 기능.

## 다중 파일 동기화 (2026-11-22)

- `file-registry.ts`: 로그인된 브라우저 조사에서 확인한 디자인 파일만 등록. 앱 10, 플그 14, 크루 10, 공홈 5개. FigJam·Slides·디자인플랫폼은 등록하지 않음.
- 현재 작업실도 포함한다(이번 사용자 요청으로 기존 제외 정책을 변경). 이름에 문서·기획·회의용·draft가 있어도 제외하지 않는다. 작업 완료 여부는 `unknown`이다.
- 크루의 옛 Design System 1개는 `library-review`: 읽고 상태를 기록하지만 서비스 검색 결과에는 새로 반영하지 않는다. 역할 변경 전 내부 검토가 필요하다.
- 파일 레지스트리의 이름은 최초 조사 표기다. 동기화 시 실제 파일명·버전을 읽는다. 폴더 이동 여부는 REST 파일 조회만으로 재검증하지 못하므로 소속 변경 시 레지스트리 재검토가 필요하다.
- 자동 폴더 발견은 아직 없다. 새 파일은 같은 형식으로 등록한다. 추후 발견 도구가 동일한 `FileSource[]`를 제공하도록 확장할 수 있다. 클라이언트가 임의 파일 키를 동기화 요청에 넣을 수는 없다.
- `[PD] 문서 모음`은 앱·플그·크루 페이지와 공홈+어드민 두 페이지를 보존한다. 공홈 읽기에서는 기존 `viewfinder:index:어드민`도 병합하며 해당 저장 키를 삭제하지 않는다.
- `id`는 기존 nodeId를 유지한다. 고유 키는 `screenIdentity(screen)`의 `fileKey/nodeId`다. 출처 필드는 선택 항목으로 추가해 이전 인덱스도 읽는다.

### 임시 생성 → 검토 → 명시적 반영

`POST /api/index-sync`, 기존 비밀번호 인증 유지:

1. `{action:"start",team:"앱"}`: 작업 준비. 실제 Figma 조회는 읽기 전용이다.
2. `{action:"continue",team:"앱"}`: 시간 예산 안에서 파일 메타데이터·구역을 읽는다. `finished:true`는 **임시 결과 완성**이며 검색 인덱스 교체가 아니다.
3. `{action:"status",team:"앱"}`: `sources`, 파일별 `files`, `draft`, `pending`, 기존 `index`를 확인한다.
4. `{action:"publish",team:"앱"}`: 검토 후 별도로 호출할 때만 검색 인덱스에 반영한다. 직전 인덱스 백업을 저장한다.
5. `{action:"retry",team:"앱"}`: 실패·검토 파일만 재시도. 다른 파일의 성공한 임시 결과를 유지한다.

상태: pending/success/unchanged/failed/review. 이 README 작성 작업에서는 운영 동기화를 실행하지 않았다. 레지스트리 등록과 실제 파일별 성공은 다르다.

- 파일 버전이 같으면 상세 구역을 다시 읽지 않는다. 변경된 파일은 모든 관련 구역을 다시 읽으며 파일 내 세부 변경 노드만 증분 수집하지는 않는다.
- 파일을 읽는 중 버전이 바뀌면 실패로 남기고 이전 결과를 보존한다. 다음 동기화·재시도로 갱신한다.
- 401, 403, 404(삭제 또는 접근 불가), 429를 구분한다. 404만으로 삭제를 확정하지 않으며 파일 누락·조회 실패로 이전 데이터를 지우지 않는다.
- 429의 Retry-After 전에는 추가 구역을 요청하지 않는다. 웹에서 안내된 시간 후 이어서 실행한다.
- 성공 파일만 새 결과로 교체하며 실패·검토 파일의 이전 결과는 유지한다. 화면 0개는 자동 삭제 대신 검토 상태다.
- 검색 데이터만 저장한다. 원본 노드 응답, 이미지, 인증 값은 job/stage/index에 저장하지 않는다.
- 실행 잠금: Redis NX/만료/소유자 확인 해제. 로컬은 임시 파일 잠금. 동일 팀 중복 시작·반영을 거부한다.

### API 호출량·한계

- 변경 파일 출처당 메타데이터 2회(시작/완료 버전 확인)+최상위 SECTION/FRAME/GROUP마다 노드 조회 1회. MDS 대조 4회/작업 시작.
- 변경 없는 출처는 메타데이터 1회. 공홈 아카이브는 한 파일의 두 페이지를 독립 출처로 관리한다.
- 동기화는 검색과 분리. 검색 시 Figma 상세 조회·이미지 분석을 추가하지 않는다. 미리보기는 선택 화면만 기존처럼 조회한다.
- 큰 SECTION은 요청 하나가 클 수 있다. 수만 레이어 파일, Redis 값 크기·요금, 시간 한도는 실제 환경에서 추가 검증해야 한다.
- 컨테이너 판정은 크기·형제 간 거리 기반 휴리스틱이다. 대형 카드나 비표준 화면 크기는 별도 검수가 필요하다. 전체 계층·스크린샷을 저장하지 않는다.

## 동기화 방법 (웹)

1. 배포 주소의 `/sync` 접속
2. 팀 비밀번호 입력 (팀 채널에서 확인)
3. 팀 공용 Figma 토큰이 등록되어 있는지 확인 (처음 한 번, 또는 만료됐을 때 `/sync` 아래 "팀 공용 Figma 토큰"에서 등록·교체)
   - Figma → Settings → Security → Personal access tokens에서 생성 (기간은 최대로, 약 90일)
   - 권한은 읽기 전용 2가지만 선택: 파일 내용 읽기, 디자인 시스템(컴포넌트·스타일) 읽기
   - `[PD] 문서 모음`과 MDS v1·v2 파일을 볼 수 있는 계정 필요
   - 등록한 토큰은 인덱스와 같은 저장소(Redis)에 보관하며 화면·응답·로그에 다시 보여 주지 않음. 동기화하는 사람마다 입력하지 않음
4. 팀 선택 후 "임시 인덱스 만들기"
5. 끝날 때까지 화면 유지 후 파일별 상태 확인, 필요한 경우 "검토한 임시 인덱스 반영"

- 동기화가 끝나기 전에는 이전 인덱스가 그대로 사용됨
- 같은 팀 페이지는 동시에 한 번만 실행 가능 (중복 실행 시 안내 문구 표시)
- 동기화 주기는 아카이브 업데이트 시 (한 기수에 한 번 정도)

## 인덱스 읽는 방법 (2-1 등 다른 기능)

```ts
import { getTeamIndex } from "@/features/1-1-index-sync/sync";

const index = await getTeamIndex("앱"); // TeamIndex | undefined (동기화한 적 없으면 undefined)
index?.screens; // IndexedScreen[]
```

- 형식은 `src/lib/types.ts`의 `TeamIndex`, `IndexedScreen`, `MdsElement` 참고
- 서버 코드에서는 위 함수로 직접 조회 (Redis 접속 정보가 서버 환경 변수에 있음)
- 브라우저에서는 `POST /api/index-data`로 조회
  - 헤더: `x-team-password`
  - 본문: `{ "team": "앱" }`
  - 응답: `TeamIndex` (동기화한 적 없는 팀은 404)
  - Figma 토큰 불필요 (저장된 인덱스를 그대로 반환)
  - 새 클라이언트는 `{team,paginated:true,cursor:0}`로 약 1MB씩 읽고 `nextCursor`를 따라간다. 후속 요청의 `snapshot`은 첫 응답의 syncedAt이다. 읽는 중 갱신되면 409로 재시도를 안내한다.
  - 기존 요청 `{team}`의 전체 응답 형식도 유지한다. 대형 인덱스에서는 새 분할 요청을 사용해야 한다. 제외 목록 상세는 동기화 status에서 확인한다.

## 화면 이미지 (2-4 등)

- 디자인 원본은 저장하지 않으므로 화면 이미지는 필요할 때마다 Figma에서 받아 옴
- 동기화와 이미지는 `/sync`에서 등록한 팀 공용 Figma 토큰(읽기 전용) 하나로 Figma를 읽음 (`figma-token.ts`)
  - `POST /api/figma-token` (헤더 `x-team-password`, 본문 `{ "action": "status" | "set" | "clear", "token"? }`, 응답 `{ configured, savedAt }`)
  - 토큰은 유효기간이 있음(최대 약 90일). 만료되면 동기화·이미지 API가 "토큰이 만료됐습니다" 안내를 돌려주므로 `/sync`에서 새 토큰으로 교체
  - 토큰이 등록되어 있지 않으면 503
  - ※ 팀 합의 전: AGENTS.md의 "Figma 토큰은 브라우저에만 저장"과 달라지는 부분이라 채널 합의 후 병합
- `POST /api/screen-image`
  - 헤더: `x-team-password`
  - 본문: `{ "team": "앱", "fileKey": "실제 파일 키", "nodeId": "202:18381", "scale": 1 }`
  - 서버에서 해당 팀의 등록 파일 및 실제 인덱스 내 프레임인지 검사. 이전 nodeId 전용 요청은 PD 파일의 등록 화면에 한해서만 호환한다.
  - 응답: `{ "nodeId": "...", "url": "임시 이미지 주소" }`
- 임시 주소는 일정 시간 후 만료되므로 보여 줄 때마다 새로 요청

## 인덱스에 담는 내용

- 화면 판정 (`screen-rules.ts`): 이름이 아니라 크기와 내용 구조로 판정
  - 폭 300px 이상, 높이 400px 이상, 폭이 높이의 2배 이하
  - 컴포넌트·도형 없이 글만 있는 프레임(메모, 더미 글) 제외
  - 제외한 프레임은 이유와 함께 `excluded`에 저장
- 제외 대상: 숨겨진 레이어, 화면 영역 밖에 놓인 글·컴포넌트·토큰
- `components`: 화면에 쓰인 컴포넌트, MDS v1·v2 파일의 컴포넌트 목록과 대조해 `isMds`, `mdsVersion` 판정
- `tokens`: MDS 파일에 있는 스타일(토큰)만 저장
- `elements`: 화면 속 MDS 컴포넌트와 위치·크기
  - MDS가 아닌 컴포넌트(시스템 UI 포함)와 MDS 컴포넌트 안쪽 컴포넌트는 제외
  - 화면 영역 밖 요소는 제외

## 알아둘 점

- 동기화 결과는 공용 토큰 계정의 Figma 접근 권한에 따라 달라질 수 있음 (일부 파일을 못 보는 계정이면 일부만 생성)
- 컴포넌트가 MDS 파일 목록에 없으면 MDS가 아닌 것으로 판정
- 스크롤해야 보이는 화면 아래쪽 내용이 프레임 밖에 있으면 검색 대상에서 제외
- Figma 파일 읽기만 수행 (생성, 수정, 이동, 삭제 코드 없음)

## 로컬 개발

- `.env.local`에 `TEAM_PASSWORD` 입력
- Redis 환경 변수가 없으면 임시 폴더의 파일에 저장 (개발 전용)
- `npm run dev` 실행 후 `/sync` 접속

## 공홈 작업실 수집 및 Description 제외

공홈 검색은 공개 홈페이지와 과거 어드민 인덱스를 함께 읽지만 두 화면 역할은 구분한다. 레지스트리 등록만으로 파일의 화면이 Redis에 수집된 것은 아니다. 실제 수집된 fileKey와 출처를 함께 확인해야 한다.

사용자 요청에 따라 `Description` 설명판과 그 설명 구역의 하위 프레임은 수집·기존 인덱스 읽기·MCP 가져오기·AI 검색 후보 단계에서 제외한다. 실제 화면 안에 표시되는 description 텍스트와 입력 필드는 지우지 않는다. 기존 Redis 레코드를 파괴적으로 삭제하지 않고 읽을 때 제외 내역으로 남긴다.

세로 스크롤 웹페이지 안의 섹션 사이 간격만으로 여러 독립 화면이라고 판정하지 않는다. 가로로 떨어진 형제 화면과 단일 래퍼 분해는 유지한다. 따라서 긴 공홈 메인을 hero·records·projects로 쪼개는 오탐을 방지한다. 화면 역할 이름이 맞는 후보는 파일별·페이지별 탐색 슬롯에도 남기되, 이름만으로 정답을 확정하지 않는다.

이번 요청에서 사용자가 39기 공홈 작업실도 포함하도록 명시적으로 허용했다. 이 예외는 다른 팀의 현재 기수 작업실 수집 규칙을 변경하지 않는다.
