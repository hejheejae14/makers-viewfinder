# MCP JSON 가져오기

관리자 화면: `/admin/mcp-import` · 서버 API: `POST /api/admin/mcp-import`.

Figma/Gemini를 호출하지 않고 이미 수집한 `TeamIndex` JSON의 화면만 기존 인덱스에 추가한다. REST의 파일 단위 교체는 사용하지 않는다. 검색 알고리즘·프롬프트·공통 데이터 형식은 변경하지 않는다.

## 인증과 운영 준비

- 기존 `TEAM_PASSWORD` 인증에 `MCP_IMPORT_ADMIN_PASSWORD` 인증을 추가한다. 기존에는 별도 관리자 인증이 없어 이 기능에 한해 별도 비밀번호를 둔다.
- 관리자 비밀번호는 팀 비밀번호와 다른 16자 이상의 영문·숫자·기호 조합을 사용한다. `.env.local` 및 Vercel의 서버 환경변수에만 설정한다. `NEXT_PUBLIC_` 변수, JSON 파일, Git에 넣지 않는다.
- 미설정·16자 미만·팀 비밀번호와 같으면 서버가 기능을 잠근다. 화면 주소를 알아도 인증 없이 검토·반영·저장소 읽기는 불가능하다.
- 입력한 비밀번호는 화면 메모리에서만 사용한다. 새 브라우저 저장 기능·로그는 없다. Redis 자격증명은 서버에서만 사용한다.
- Vercel의 기존 Redis 환경변수가 올바른 운영 저장소를 가리키는지 확인한다. Mac의 임시 파일·개발용 파일 저장소는 Vercel로 자동 전송되지 않는다.

## 사용 순서

1. 기능을 배포하고 서버 환경변수를 설정한 뒤 **배포 사이트**의 `/admin/mcp-import`로 접속한다. 이 문서 작성 작업에서 실제 배포·환경변수 설정·운영 반영은 하지 않았다.
2. 팀 비밀번호와 관리자 비밀번호를 입력하고 팀을 선택한다.
3. Mac의 `/private/tmp/viewfinder-mcp-app-poc/index.json`을 선택한다. 파일 선택창에서 `Command+Shift+G`로 경로를 입력할 수 있다. 데이터 파일을 Git에 추가할 필요는 없다.
4. `검토하기`를 누른다. 관리자 인증 후 JSON이 서버로 전송되고 **별도의 MCP 초안**만 저장된다. 기존 화면·운영 키는 변경하지 않는다.
5. 기존 수, 추가 수, 중복·충돌·거부 수, APP 정답 프레임 포함 여부, 삭제·변경 0개를 확인한다. 기존 운영 298개에 중복 없는 4개를 추가하는 경우에만 예상 총수는 302개다.
6. 직접 수집 근거와 미수집 범위를 확인한 뒤 체크박스를 선택하고 `운영 인덱스에 새 화면 추가`를 누른다. **이 버튼이 실제 운영 쓰기다.**
7. 같은 배포 사이트 `/search`에서 다시 검색한다. 정답 프레임이 데이터에 포함되는 것을 보장하는 기능이지 Gemini의 정답 순위·의미 해석을 보장하는 기능은 아니다.

로컬 화면은 로컬 서버의 저장소에 연결된다. Vercel 저장소에 반영하려면 배포된 화면을 사용해야 한다. 실제 REST 동기화가 진행 중이거나 검토 초안이 남아 있으면 MCP 검토·반영을 차단한다. 기존 REST 초안을 임의로 삭제하지 않는다.

## 검증과 병합 정책

- 클라이언트 파일 한도 1.5MB, 서버 요청 한도 2MB, 화면 1~500개. 요청 크기는 `Content-Length` 없이도 검사한다.
- 기존 `TeamIndex`/`IndexedScreen`의 필수·선택 필드와 중첩 자료형을 검사한다. 다른 추가 필드는 거부한다. 파일 전체의 원본 트리를 업로드하는 기능이 아니다.
- 팀·파일은 서버 레지스트리 기준이다. PD 문서 모음은 등록된 팀 페이지도 확인한다. URL의 fileKey/nodeId 일치와 화면 내용의 검색 근거 존재를 검사한다.
- `fileKey + nodeId`가 같고 수집 시각 외의 데이터도 같으면 중복으로 건너뛴다. 시각 외의 필드가 다르면 충돌이다. 일부 값이 같아 보인다는 이유로 자동 덮어쓰지 않는다.
- 충돌·거부가 하나라도 있으면 전체 반영을 막는다. 충돌은 업로드 JSON에서 해당 화면을 제외하거나 별도 검토한다. 기존 데이터를 고쳐 통과시키지 않는다.
- 원래 화면·텍스트·컴포넌트·토큰 배열의 순서는 유지한다. `evidenceRefs`는 공통 인덱스에 저장되는 필드가 아니라 검색 시 이 배열에서 생성되므로 순서를 바꾸지 않는 방식으로 보존한다.
- `files`/`excluded` 입력은 운영 데이터 갱신에 사용하지 않는다. 기존 운영의 파일 상태·제외 목록을 그대로 보존한다. 일부 화면을 파일 전체 성공으로 표시하지 않는다.
- 원문 텍스트가 실제 Figma와 같은지, 숨겨진 레이어가 제외됐는지, 전체 Empty인지 일부 영역 Empty인지는 JSON 형식 검사만으로 증명할 수 없다. 수집자의 원본 근거 검토가 필요하다.
- 컴포넌트·토큰 빈 배열을 채우거나 실제 부재로 단정하지 않는다. 가져오기 이력의 수집 범위는 `partial`, 컴포넌트·토큰 수집 범위는 `unverified`로 남긴다. 기존 검색·MDS 화면은 수정하지 않았다.

## 저장소와 동시 작업

- 운영: `viewfinder:index:<팀>`
- MCP 검토: `viewfinder:mcp-import:draft:<팀>` — 팀당 최신 검토 하나, 15분 유효. 다른 검토가 생성되면 이전 반영 요청은 거절된다.
- REST 초안: `viewfinder:multi-draft:<팀>` — MCP 초안과 분리.
- 공통 잠금: 기존 `viewfinder:multi-lock:<팀>`을 REST와 함께 사용한다.
- 백업: 기존 형식 `{ index: 이전값 }`, 키 `viewfinder:multi-backup:<팀>:mcp-<검토 ID>`.
- 최근 가져오기 이력: `viewfinder:mcp-import:last:<팀>`.

검토 시 운영 인덱스 전체의 해시를 보관하고, 반영 시 잠금 안에서 최신 값을 다시 읽어 비교한다. `syncedAt`이 그대로여도 데이터가 달라지면 중단한다. 같은 기본 데이터에만 추가하며 다른 팀 키는 쓰지 않는다. 백업이 실패하면 운영 쓰기를 하지 않는다.

개별 저장소 명령으로 백업→운영 저장→이력 저장→초안 삭제를 수행한다. 전체 Redis 트랜잭션은 아니다. 운영 저장 직후 연결이 끊기면 화면에 오류가 떠도 반영됐을 수 있으므로 검색 인덱스·백업을 확인하고 다시 검토해야 한다. 이전 검토 ID를 다시 호출해 중복 추가하지 않는다. 백업 복원 버튼은 이번 범위에 포함하지 않았다.
