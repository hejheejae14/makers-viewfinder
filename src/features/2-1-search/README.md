# 2-1. 팀 선택 및 화면 검색

선택한 팀의 인덱스에서 Gemini로 검색 의도를 해석하고, 원문 근거를 검사한 결과를 공통 `SearchResponse`로 반환합니다.

## 검색 범위와 호환성

- 기존 `POST /api/index-data` 및 `TeamPage`, `TeamIndex`, `SearchResult`, `SearchResponse` 형식을 유지합니다.
- 인덱스의 팀이 요청 팀과 다르면 중단하고, 화면별 팀이 다른 항목도 AI에 전달하지 않습니다.
- 기존 팀 선택 UI·결과 목록·첫 번째 결과 선택·Figma 원본 링크·미리보기를 유지합니다.
- 이름·구역·파일명으로 탐색 범위를 제거하지 않습니다. 받은 인덱스 전체에서 후보를 계산합니다.
- `1-1-index-sync/file-registry.ts`의 팀별 디자인 파일과 `[PD] 문서 모음`을 사용합니다. 폴더 자동 발견은 아니며 등록한 파일 범위입니다. 앱·플그·크루·공홈 4개 선택을 제공하고 과거 어드민은 공홈에 읽기 병합합니다. 현재 작업실도 등록합니다.
- `candidate-search.ts`의 기존 label/aliases 함수와 숫자 score는 3-2 사용 사례 비교 호출자와 호환됩니다. score는 검색 보조 값이며 확률이나 정확도가 아닙니다.

## 동작

1. `query-understanding.ts`, `gemini-validation.ts`: 조건을 service/screen/function/state/component/property/platform/text/token/cohort로 구분하고 must/should/exclude, 원문 인용 sourceText, 범위 scope, 같은 요소 관계 relatedTo를 보존합니다. 기수는 검색어에 명시한 경우에만 추가하며 파일의 기수 표기를 화면 제작 기수로 확정하지 않습니다.
   - 인용은 대소문자·공백·유니코드 표기 차이를 정규화해 비교합니다. 연결이 불확실하면 경고와 `sourceVerified: false`를 남기고 검색을 계속하며 해당 조건을 정답 근거로 확정하지 않습니다. 잘못된 조건 구조, 중복 ID, 존재하지 않는 관계는 거부합니다.
   - 명시적인 홈·빈 상태·앱서비스 조건 누락을 원문에서 복구하고 경고를 남깁니다.
   - 이 검사는 모든 한국어 문장의 누락을 완벽히 감지하는 의미 검증기가 아닙니다. 다른 기능·복합 제외·선호 표현은 실제 검색 추적으로 추가 검증해야 합니다.
2. `evidence.ts`, `candidate-search.ts`: 역방향 부분 문자열 비교를 제거하고 실제 문구·속성과 이름·구역 힌트를 구분합니다. property.relatedTo는 같은 owner의 컴포넌트 사용 정보에서만 직접 일치로 셉니다.
   - 직접 일치한 필수조건 수 → 전체 직접 일치 수 → 미일치 수 → 힌트 순으로 후보를 고릅니다.
   - 후보 상한은 파일 수×3을 기준으로 20~60개입니다. 약 1/3(최소 5개)은 파일·페이지별 관련 후보 탐색에 사용합니다. 작은 인덱스는 키워드가 없는 화면도 검토합니다.
   - 유한한 후보 상한 때문에 의미가 전혀 다른 표현으로 기록된 정답 누락 가능성은 남습니다. trace.candidateTruncated로 확인합니다. 후보 증가로 토큰 사용량은 늘 수 있습니다. 기본 Gemini 호출은 2회이며 503 재시도 시 최대 4회입니다.
3. `judge-prompt.ts`, `gemini.ts`: 동일한 Gemini 모델로 해석 1회, 판정 1회를 호출합니다. 원문 근거 ref와 조건별 확인됨/추정/확인 불가/불충족, 질적 관련도와 순서를 받습니다.
4. `verification.ts`: 근거 ref를 실제 인덱스와 대조합니다. 임의의 문구·속성은 결과 근거로 사용하지 않습니다.
   - 이름·구역만 인용하면 추정으로 낮춥니다.
   - 컴포넌트와 속성은 같은 사용 정보/요소 owner인지 검사합니다.
   - 원문에 없는 근거, 누락된 조건, 화면 전체 상태를 증명하지 못한 작은 요소는 정확한 정답으로 확정하지 않습니다.
   - State=Empty와 State=Filled가 함께 있으면 전체 상태는 추정으로 남깁니다.
   - 미확인과 반대 근거가 있는 불충족을 구분합니다. 단, 인용한 데이터의 존재를 검사하는 것이며 AI의 모든 의미 판단이 참임을 수학적으로 증명하지는 않습니다.
5. `search-pipeline.ts`: 검증 결과를 정렬하고 기존 응답으로 반환합니다.

## 최종 순위

1. 모든 필수조건이 직접 확인되고 제외조건도 안전하게 확인된 정답 후보
2. 명시적인 필수조건 불충족은 없고 관련성은 높지만 일부 근거가 부족한 후보
3. 그 외 일부만 일치하거나 명시적인 불충족이 있는 관련 후보

같은 등급 안에서는 AI가 반환한 관련도 순서를 유지합니다. `irrelevant`와 확인된 제외조건은 반환하지 않습니다. `low` 또는 알려진 비표준 응답 `불충족 후보`는 실제 직접 단서가 있는 경우에만 하위의 부분 일치 추천으로 표시하며 정답으로 승격하지 않습니다. 임의의 다른 verdict나 잘못된 자료형은 계속 오류입니다. AI가 빈 목록을 반환하면 실제 단서가 있는 후보 최대 3개만 부분 일치로 추천합니다. 추천 이유와 미확인 조건을 표시하며 무관한 결과로 개수를 채우지 않습니다. 원문 연결이 불확실한 조건이 있으면 정답으로 확정하지 않습니다.

## 데이터 한계

- 새 인덱스는 components.instanceId를 보존합니다. 이전 인덱스에는 ID가 없으므로 같은 사용 정보에 속한 variant까지만 확인할 수 있습니다.
- elements는 ID·소속 텍스트·위치를 보존하지만 MDS 요소 일부만 수집합니다. 모든 프레임 계층을 제공하지 않습니다.
- 평탄화된 텍스트만으로 화면 전체와 카드 일부의 상태, 복수 화면 컨테이너를 완벽하게 구분할 수 없습니다. 불분명한 경우 추정/확인 불가로 남겨야 합니다.
- 이미지·design context 추가 조회 및 재인덱싱은 하지 않습니다. 검색 판정의 추가 Figma API 호출은 0회입니다.
- 근거 목록과 조건별 판정이 늘어 Gemini 입출력 토큰 및 지연은 증가할 수 있습니다. 실제 지연·토큰 사용량은 배포 환경에서 측정해야 합니다.

## Gemini 응답 형식 및 오류 진단

일반 검색과 MCP 테스트 검색은 같은 `createGeminiSearchAi`/`requestGeminiJson`을 통해 JSON 모드로 요청합니다. interpret·judge 모두 `responseMimeType: "application/json"`, temperature=0.1, store=false와 기존 모델·API 버전·사용자 키를 유지하며 `responseJsonSchema`와 `responseSchema`는 전송하지 않습니다. Git의 기존 요청 구성을 최소 복구한 것이며 과거 파일 전체를 되돌리지 않았습니다. 강화된 프롬프트가 JSON 필드·자료형·조건 관계를 안내하고, `gemini-schema.ts`의 `INTERPRET_SCHEMA`/`JUDGE_SCHEMA`는 엄격한 브라우저 검증 기준으로 계속 사용합니다. 빈 문자열·빈 배열·길이 상한·필수조건·근거 검증을 완화하지 않습니다. 잘못된 항목을 삭제하거나 기본값으로 통과시키지 않습니다. 기존 비엄격 파서 호출의 호환성도 유지합니다.

`gemini-error.ts`는 network / http-api / empty / json / schema / semantic / timeout / payload 오류를 구분합니다. MCP 테스트 화면은 단계·HTTP 상태·finishReason·필드 경로와 개수 요약만 메모리에 보관합니다. 키·인증 헤더·검색 원문·후보 및 응답 원문을 진단으로 기록하지 않습니다. 일반 검색도 동일한 어댑터와 오류 메시지를 사용합니다. 사용자 개인 키 입력·저장·Google 직접 호출 방식, 근거 검증 및 관련도 순위 로직은 유지합니다.

오프라인 테스트: `gemini.test.mjs`, `gemini-retry.test.mjs`, `precision.test.mjs`. 실제 fetch를 메모리 응답으로 대체하여 네트워크/API 요청 없이 실행합니다. 양쪽 요청의 서버 스키마 미전송, 엄격한 응답 검증과 부분 일치/근거 검증을 함께 검사합니다. 실제 JSON 모드 검색의 성공 여부와 정확도는 별도의 실 API 검증이 필요합니다. 공용/환경변수 키 대체는 없습니다.

`gemini-retry.ts`는 검색의 HTTP 503에만 단계별 최대 1회 재시도합니다. 기본 1~1.5초를 기다리며 `Retry-After`가 길면 존중하고, 10초를 초과하면 추가 요청하지 않습니다. 취소 시 재시도하지 않습니다. 400·429·네트워크·응답 검증 오류는 재시도하지 않습니다. 일반 검색과 MCP 테스트 모두 실행 전에 추가 사용량을 안내합니다. MCP 요청 횟수는 실제 시도 수를 셉니다. A~D/D 진단은 재시도 없이 기존 호출 한도를 유지합니다. 서버의 지속적인 503 자체를 해결하는 기능은 아닙니다.

HTTP 실패 시 `gemini-http-error.ts`가 Google 오류 본문에서 허용한 숫자 code, status/reason 열거값 및 현재 요청·스키마에 속한 필드 경로만 추출합니다. 오류 message, description, metadata와 임의 필드명은 전달하지 않습니다. 빈 본문·HTML·잘못된 JSON·수신 실패도 HTTP 오류로 유지하고 별도 bodyState를 제공합니다. 이전 요청의 오류 본문을 복구하는 기능은 아니며 실제 400 원인은 아직 미확인입니다.

개발용 A~D/D 전용 진단은 검색에서 분리된 스키마 실험으로 유지하며 기본 화면에서는 접어 둡니다. `INTERPRET_REQUEST_SCHEMA`는 이 실험의 D에서만 사용합니다. 사용자 보고의 A/B/C 성공·D 400은 스키마 적용과의 연관성을 좁히지만 특정 키워드가 단독 원인임을 증명하지는 않습니다. 전송 스키마를 계속 수정해 일반 검색에 적용하는 흐름은 중단했습니다. 브라우저 검증 스키마와 검색 정확도 파이프라인은 유지합니다.

## 판정 요청 경량화와 대기시간 제한

- `judge-payload.ts`는 전송 단계에서 텍스트·컴포넌트·variant·토큰을 `evidence` 한 곳에만 담습니다. 이름·구역·출처도 기존 evidence에 있고, 구조·프레임 크기·요소 위치는 별도로 유지합니다. 원래 인덱스, 후보 선정 수(20~60), 화면 순서, ref/owner 번호는 바꾸지 않습니다.
- 판정 입력 JSON은 최대 60,000자, 후보 하나는 최대 12,000자입니다. 문자 수는 토큰 수·모델 컨텍스트 한도가 아닙니다. 전체 요청 본문도 300,000바이트를 넘으면 API 호출 전에 `payload` 오류로 중단합니다.
- 모든 후보에 공간을 배분합니다. 큰 후보는 조건별 단서·제외조건·이름/구역·variant를 우선해 원문 단위로 선택합니다. 컴포넌트 이름과 variant는 같은 owner로 연결하며 위치도 보존합니다. 문구를 잘라 가짜 인용으로 만들지 않습니다. 반대로 키워드로 표현되지 않은 의미 단서가 생략될 가능성은 남습니다.
- `coverage`로 생략 범위를 AI에 알립니다. 브라우저는 실제 전달한 ref만 유효한 AI 근거로 인정합니다. 일부 내용이 생략되면 정답으로 확정하지 않고 부분 일치로만 표시합니다. 추정·제외조건·전체 Empty와 부분 영역 Empty에 대한 기존 검증은 유지합니다.
- `gemini-deadline.ts`는 해석 20초, 판정 40초 한도로 fetch·응답 본문·503 재시도 대기 전체를 묶습니다. 시간 초과나 사용자 취소는 추가 요청을 하지 않습니다. 해석을 통과한 경우 두 단계의 AI 대기 상한은 합계 약 60초이며, 인덱스 로딩·브라우저 처리 시간은 별도입니다. A~D 진단은 이 검색 경로와 분리돼 있습니다.
- 503 재시도는 단계별 1회 그대로입니다. 같은 전송 본문을 재사용하고 실패 응답 스트림을 정리합니다. 재시도 횟수나 모델을 늘리거나 공용 키로 전환하지 않습니다.
- MCP 테스트 화면에는 판정 입력 문자 수·후보 수·생략 수만 브라우저 메모리에 표시합니다. 진단을 서버로 보내거나 영구 저장하지 않습니다.

오프라인 측정(실제 Gemini 토큰·지연 측정 아님): 기존 MCP 화면 4개는 판정 입력 11,523자 → 9,958자로 약 14% 감소했고 근거 생략은 0개였습니다. 큰 합성 요청은 후보 60개를 유지한 채 약 197만 자 → 54,254자로 줄었지만 일부 근거를 생략했습니다. 이 합성 수치를 실제 운영 성능·정확도 개선율로 해석하면 안 됩니다.

실제 Gemini가 경량화된 입력을 해석하는 품질, 운영 검색 지연과 503 빈도는 배포 후 같은 검색어로 비교해야 합니다. Google 서버의 과부하 자체를 이 변경으로 해결할 수는 없습니다. 운영 인덱스와 Figma 인증·동기화는 변경하지 않습니다.
